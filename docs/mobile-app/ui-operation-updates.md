# 画面操作の更新

予約の照会で記録が見つからないと、表示は「結果不明」のままです。Core は同じ要求の新しい照会券を発行します。画面で更新後に押したボタンは、新しい券を現在の実行先へ渡します。

## 適用する制約

| 適用対象 | 防ぐ問題 | 許される例 | 違反例 | 保証と限界 |
| --- | --- | --- | --- | --- |
| DCA の判断契約 | 仕様にない再試行や、古い券を別の操作へ付け替える | 閉じた結果型を変換と操作選択で網羅し、表示時点の券を Core へ渡す | 結果不明の照会を新規送信で代用する。クリック時に最新の券を取得してから送る | 型・可視性とコンパイル負例で違う券や外部構築を拒否する。現在性・対象・期限・重複は Core とその実行テストで確かめる |
| 操作を持つ入力と更新境界 | 操作の差が表示の一致で落ちる | 種別・宛先・券・対象・引数・可否を含めて比較し、比較した値から実行する | 文言だけの比較で通知を省く。比較用 ID と別に実行クロージャを渡す | 不変な型と画面テストを使う。個別の構文検査から任意の比較やクロージャの意味は判断できない |
| SwiftUI の同一性と更新 | 子ビューに更新が届かない。券の更新で UI 状態が消える | フローを識別する ID を保ち、操作入力が変われば子に渡す | 表示だけを比較する `EquatableView` で操作を持つ子を囲む。券を `.id` に使う | ホストした画面を操作して券と UI 状態を観測する。実描画や `body` の回数は判定に使わない |
| Kotlin 共通層の通知 | `StateFlow` が新しい操作を同じ値として扱う | 操作に使うプロパティを比較に含める。参照で比較する場合は、同じインスタンスに別の操作を入れ直さない | data class の本体へ券を移し、自動生成される `equals` から外す | 比較と通知を実行テストで確かめる。手書きの `equals` や入れ子も確認対象になる |
| Compose のイベント接続 | 再コンポジション後も古いクロージャを使う | 現在の不変な操作入力からイベントを作る。明示的にキャッシュする場合は実行内容の差をキーに含める | `remember(label) { { check(ticket) } }`。実行先の変更をキーに含めない | ホストした Compose で反映を待ってボタンを押す。Strong skipping や `rememberUpdatedState` で上流が除いた更新は復元できない |

この例では、画面入力の接続をコードで表します。生成は、同じ規則から接続を導ける箇所が増えた場合の選択肢です。生成しても業務上の分岐と必須の接続は利用側に残ります。

古い券を受け取った同じ Core は現在の券と照合します。別の実行先へ画面が切り替わっても、すでに作ったイベントが保持する実行先は変わりません。その実行先が券を受理するかは、その時点の状態で決まります。

## サンプルでの接続

照会と再試行に限り、画面の接続点で `RequestAction` に実行先と型付きの券を保持します。Core から画面状態への投影は券を運び、表示の分岐が該当する操作を組み立てます。実行先は ViewModel の状態の外で結び付けるため、状態から実行先への循環参照がありません。ボタンが受け取る操作は必須です。

- SwiftUI は `RequestAction` の enum と、参照を `===` で比べる `ByIdentity` を使います。enum の合成された比較と `execute()` は、同じケースが保持する券と実行先を見ます。
- Kotlin 共通層では、照会と再試行を sealed interface の data class にします。券と実行先は変更できない主コンストラクタ引数で、現在の型は参照の同一性で比較されます。初期値の後から操作を追加するプロパティや、別の操作に転送するクロージャは持ちません。
- Compose のボタンは、現在の操作値を保持するイベントを作ります。表示文言だけで通知を省く処理や、券と実行先のどちらかを欠いた `remember` を入れると、型が正しくても更新を落とせます。ホストテストと変異検査でこの経路を確認します。

開始版の照会は実画面の検証で確認できました。操作値を追加した目的は、実行先と券の組を、比較から実行まで同じ宣言で追えるようにすることです。画面は結果に応じて操作を選び、期限と外部要求の寿命は Core が管理します。

## 開始版での観測

`663407d` の SwiftUI 版と Compose Multiplatform 版を、それぞれ iOS 27.0 Simulator で起動しました。予約作成の応答を失わせ、最初の照会を「記録が見つからない」に設定します。照会後も「結果不明」と「状況を照会する」が表示され、同じボタンをもう一度押すと予約が確定しました。どちらも作成要求1回、照会2回、成立1件でした。この操作経路で、古い券が残る現象は観測されませんでした。受理された券のインスタンスと宛先を直接記録する検査には、専用の画面を使います。

開始版の SwiftUI では Core の `Store` が `AsyncStream` で値を公開し、`ReservationViewModel` が投影結果を `@Published` で通知します。Kotlin 版では `MutableStateFlow` の Core 状態を `ReservationViewModel` の `combine` と `stateIn` で投影し、Compose が購読します。券を含むカードの参照の変化が等価比較を通り、描画したカードからクリックへ券を渡します。どちらでも Core は現在の券を参照で照合します。

SwiftUI の `EquatableView` は等しい入力の子ビュー更新を省きます。Compose の Strong skipping は、安定と判定された入力を等価性、不安定な入力を参照で比較します。明示的な `remember` ではキーの等価性を使います。 `StateFlow` の等価性による通知の省略は、Compose の前に起こります。 [Apple の EquatableView](https://developer.apple.com/documentation/swiftui/equatableview) · [SwiftUI の同一性と寿命](https://developer.apple.com/videos/play/wwdc2021/10022/) · [Strong skipping](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping) · [StateFlow](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-state-flow/)

| 構成 | 版と設定 |
| --- | --- |
| SwiftUI サンプル | Xcode 27.0（27A266a）、Apple Swift 6.4、Swift 6 言語モード、iOS 16 の deployment target、iOS 27.0 SDK |
| KMP サンプル | Kotlin と Compose コンパイラ 2.3.21、Compose Multiplatform 1.12.2、Material 3 1.9.0、Lifecycle 2.9.6、kotlinx.coroutines 1.10.2、Gradle 9.3.1、JDK 21。Strong skipping はコンパイラの既定値 |
| 静的検査 | SwiftLint 0.65.1、detekt 2.0.0-alpha.3 |

## 隔離した負例での観測

SwiftUI の比較用アプリで、表示文言を固定したまま T1 と T2 を Combine に渡しました。 `removeDuplicates` を文言だけで比較する構成では、T2 の公開後に押したボタンから T1 が届きました。券の参照も比較すると T2 が届きました。別の `EquatableView` の試作では古い券は残りませんでした。実測した通知の重複排除と、祖先の比較で起こり得る更新の省略は分けて扱います。

Compose の `ActionClickTest` では、製品の予約状況画面を JVM 上にホストします。照会中を表示せず、同じ「結果不明」のまま新しい券を渡してポインタ入力を送ります。Core が現在の券の参照を照合して R1 の照会を受理し、回数が1から2へ増えることで T2 の到達を確認します。`ViewModelStateClickTest` は、同じ遷移を画面 StateFlow の購読からクリックまで通します。旧券のままなら、古い操作として拒否され、照会回数は増えません。

同じ券で ViewModel だけを差し替える試験では、再試行の期限切れを Core が拒否し、その通知を受けた ViewModel を観測します。旧 ViewModel が通知を受ける負例と、新しい ViewModel が受ける正例を確認しました。ホストのカウンターと画面のスクロール位置は券を更新しても維持されます。

`examples/reservation-mobile/` で次を実行します。変異検査は一時コピーに変更を加えてテストの失敗箇所を照合します。操作を最初の値に固定、実行先だけでキャッシュ、券を等価性から除外、券ごとのキーでカードを再生成する4つの変異で、それぞれ期待したテストが失敗しました。

```sh
./gradlew :ui:jvmTest
./gradlew verifyActionMutations
```

SwiftUI の `ActionClickUITests` では、テスト用アプリに製品の `ReservationStatusView` と `ActionButton` をホストします。券だけを替えるケースでは、テスト用の観測欄で T2 の配信を待ってから、同じ「状況を照会する」を押します。Core が参照の一致で T2 を受理し、同じ要求への照会が1回増えます。実行先だけを ViewModel A から B へ替えるケースでは、同じ券を用いた照会が処理中なので Core は二度目を拒否します。この拒否通知を B が受け取ることまで確かめます。ホストの `@State` とスクロール位置も観測します。

SwiftUI の負例は、操作を `@State` に初期値として保持する場合、表示だけで Combine の通知を除く場合、券だけを識別に使って実行先を保持する場合です。前二者は照会を増やさずに古い券を拒否し、最後の負例は A が拒否通知を受け取りました。

起動済みの iOS Simulator の ID を `<UDID>` に入れ、`examples/reservation-ios/` で実行します。Xcode がホストの SDK とリンカーを選ぶ環境で実行してください。

```sh
sh Tools/ui-click.sh positive --device '<UDID>'
sh Tools/ui-click.sh negative --device '<UDID>'
```

| 条件 | 検査した結果 |
| --- | --- |
| 表示と券と実行先が同じ | 両実装で操作値の比較が等しく、Kotlin ではハッシュも一致する |
| 操作種別、対象、引数、可否が変わる | 照会と再試行が異なる型の券を使うこと、更新後の照会が R2 に届くこと、対象の状態に応じて操作を選び、期限切れの要求を Core が拒否することを確認する |
| 新しい表示より前のイベントが遅れて届く | 両実装の操作値のテストで、保持していた旧券を実行して拒否されること、外部要求が増えないことを確認する |
| 券の型が違う。利用側が券を構築する | 通常の利用側と別の発行モジュールでのコンパイル負例が、型の不一致とコンストラクタの不可視性で拒否されることを確認する |
| Core または画面の結果型へケースを追加する | 隔離コピーで `ActiveRequest` にケースを追加すると両言語の投影で、`RequestCard` に追加すると文言と操作選択で網羅性の診断が出る。製品コードの分岐を補った後も、テスト側で新しいケースの扱いを決める必要がある |
| 操作を比較から除く。旧操作を保持する | Compose の4種類の変異と、SwiftUI の `ActionButton` に旧操作を保持させる変異で検出する。SwiftUI の変異では三つの正例が期待した観測欄で失敗した |

検査の範囲は、予約状況に現れる照会と再試行です。操作種別の分岐は画面が持ち、対象と送る要求 ID は券から取得します。今回の操作に券のほかに渡す業務引数はありません。SwiftUI は再試行ボタンの表示にも期限の判定を使い、Compose 版は実行時の Core の判定で期限切れを伝えます。

静的検査は指定した型や部品の書き方を扱います。未指定の祖先や通知の等価性は、更新経路のレビューと画面テストで確認します。Compose の自動検査では JVM 上でポインタ入力を行い、通常の iOS 版でも Simulator で同じ照会を試しました。物理端末での検証、性能計測、利用者による評価は実施していません。 [Compose Multiplatform の UI テスト](https://kotlinlang.org/docs/multiplatform/compose-test.html) · [Xcode の UI 自動化](https://developer.apple.com/videos/play/wwdc2025/344/)

## dca Plugin への反映

Plugin 0.1.1 は、設計と検証の文書を出典とハッシュ付きで同梱します。`map` と `scan` は表示からクリックまでの経路を追い、`interview` は画面状態の寿命と実行先に未決事項があるときに確認します。`refactor` は画面を実際に操作して検証する段階を計画し、`lint` は対象境界に絞って正例、負例と限界を示します。`guide` は SwiftUI の更新について原則、調査、検査提案へ案内します。E19 は両 UI の問題例を調べるモデル評価で、評価自体は未実施です。 [E19](../../plugins/dca/evals/cases/E19-ui-operation-update.json)

変更は既存 Skill の判断と手順に収まるため、Skill の登録・起動方針・ホスト別の案内文・外部記録の形式には既存の構成を使います。両ホストの manifest と marketplace に同じバージョンを設定し、登録情報から構成図を再生成しました。 [Plugin の構成図](../../plugins/dca/docs/overview.svg)
