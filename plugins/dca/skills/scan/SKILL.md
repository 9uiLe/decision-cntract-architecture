# scan

対象フローの問題を、根拠付きで種類を分けて報告する。

## 使う場面

- DCA の適用を検討する前に、現状の問題を調べたい。
- `map` で見つかった不明点や結合を、詳しく確認したい。
- 移行の後に、合意した範囲の問題が残っていないかを確認したい。

## 読む資料

- [情報モデル](../principles/references/common/information-model.md)
- [検証](../principles/references/common/verification.md)
- [外部記録](../principles/references/common/record-storage.md)
- [同梱思想の索引](../principles/references/index.md)

指摘の種類は情報モデルの「指摘の種類」で分類する。適用する原則が必須か任意かは、索引の表で確認する。

## 手順

1. 対象の範囲と適用条件を確認する。外部記録の資料の「作業の始め方」に従い、保存先、既存のフロー、現在の変更対象を確かめる。記録があるときは、現在のソースとの対応を照合する。
2. 判断、契約、状態、副作用、利用側、保証を、根拠に沿って調べる。`map` の結果があれば、現在の対象と一致するかを確かめて使う。なければ、今回の調査に必要な対応関係をこの Skill で確認する。
3. 指摘を、違反、仕様不足、矛盾、検証不足、追加調査に分ける。任意の改善候補は、これらと分けて示す。
   - 操作を持つ画面では、表示が同じでも券や実行先が変わる経路を追う。通知と比較で変更が失われた事実、隔離した負例での再現、操作までに券が失効した場合の Core の拒否を区別する。
4. 各指摘に、次を付ける。
   - 観測した事実
   - 根拠（ファイルとシンボルなど）
   - 適用した原則
   - 影響する利用側と保証
   - 次の確認事項
5. 根拠を超える推測は、推測として分ける。
6. 調べられる事実は調査を進めて確かめる。人が選ぶ必要がある論点は `interview` へ、機械で再発を検出できそうなものは `lint` へ、修正が要るものは `refactor` へ渡す候補として示す。
7. 調べたパスの識別情報を作り、報告を外部記録に保存する。

## 出力

- 根拠別の調査報告。
- 調べた範囲と、調べていない範囲。
- 追加の調査の候補。
- 利用者に残る意思決定。
- 保存先、選択元、新しい記録かどうか、現在の変更対象。

## 完了条件

調べた範囲と未確認の範囲が示され、各指摘の分類、根拠、影響、次の確認を追える。指摘がないときも、観測した範囲で見つからなかったことと、保証の全体が成り立つことを区別する。

## 境界

- 好みや、任意のパターンを採らないことを、違反にしない。
- 仕様不足を独断で補わない。
- 依頼が scan だけのときは、コードと導入先の設定を変更しない。修正の計画と変更は `refactor` が扱う。
- 他の Skill の事前の実行を、開始の条件にしない。

## 他の Skill との関係

- 引き継ぎ skill:interview: 人が選ぶ必要がある論点を渡す
- 引き継ぎ skill:lint: 機械で再発を検出できそうな指摘を渡す
- 引き継ぎ skill:refactor: 修正の計画と変更が要る指摘を渡す
- 生成 artifact:external-record: 根拠別の調査報告と、調べた範囲
