# lint

機械で検出できる範囲と、人の判断が要る範囲を分け、検査ルールを提案する。

## 使う場面

- `scan` で見つかった問題を、継続して検出できるかを調べたい。
- 既存の detekt などで、同等の検査ができるかを確認したい。
- 新しいルールの必要性と、誤検出と検出漏れの限界を評価したい。

## 読む資料

- [検証](../principles/references/common/verification.md)
- [情報モデル](../principles/references/common/information-model.md)
- [同梱思想の索引](../principles/references/index.md)

検証は「型と Lint の確認」を使う。DCA の検査仕様は、索引が指す S03 にある。

## 手順

1. 対象のコードと環境、既存の静的解析のツールと設定、適用する原則、具体的な指摘や違反例、許可したい例を確認する。導入先の現行の版と設定から、使える機能を確かめる。
2. 検出したい事実と原則を結び付ける。命名、構文、型、依存関係など、機械が観測できる条件に分解する。
3. 既存のルールと設定で扱えるかを、一次資料と導入先の設定から調べる。似た名前のルールがあるだけで、同等と判断しない。
4. 提案を次のどれかに分類し、理由を付ける。
   - 既存のルールで足りる
   - 設定で補える
   - 独自のルールが候補になる
   - 機械で判定するには向かない
5. 提案ごとに、次を示す。

| 項目 | 内容 |
| --- | --- |
| 検出条件 | 何を観測すると指摘するか |
| 許可例 | 合意した原則のうえで、指摘してはいけない例 |
| 違反例 | どの条件に当たり、なぜ指摘するか |
| 限界 | 型の情報、実行時の状態、外部の情報など、必要でも得られないもの |
| 誤検出 | 正当なコードを指摘する可能性と、その理由 |
| 検出漏れ | 問題があっても検出できない代表的な場合 |

6. 採用するときの評価の方法と、残る確認事項を提案する。名前や階層のような代理の指標と、業務判断の意味の正しさを区別する。

## 出力

- 既存のルールとの対応の調査。
- 検査候補の仕様。許可例と違反例を含む。
- 限界、誤検出、検出漏れ。
- 採用の判断に必要な検証案。
- 根拠にしたツールの資料と版。

## 完了条件

各提案に、検出条件、例、限界、誤検出がある。既存のルールを使うか、新しく検討するかを判断できる。機械で検出できない原則も、示されている。

## 境界

- 調査と提案までを行う。ルールの実装、静的解析用の依存関係の追加、設定とビルドと CI の変更、自動修正はしない。
- lint を通ったことを、DCA への適合や業務仕様の正しさの証明にしない。
- 他の Skill の事前の実行を、開始の条件にしない。
