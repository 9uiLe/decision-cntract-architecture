# 段階移行

既存の一つの業務フローを、合意した挙動と保証を保ちながら DCA へ段階的に移す手順の共通資料。refactor が主に使い、scan と interview は変更範囲の境界を確かめるときに読む。

## 移行の単位

最初の単位は、前提、結果、次の操作の関係を追える一つの業務フローとする。ファイル数や画面数だけで切らず、対象の操作とその利用側まで含めて保証の範囲を決める。

DCA の適用は、全面適用、部分適用、適用不要のどれも認める。結果によって次の操作が変わらず、利用側に再判断を求めない処理には、型や Handler を一律に足さない。[S01]

対象外のコードを理由なく整理しない。プロジェクト全体のアーキテクチャ変更に広げない。

## 作業の種類を分ける

| 作業 | 内容 | 合意と検証 |
| --- | --- | --- |
| 構造移行 | 判断の所有、契約、依存、状態と外部操作の接続を整理する | 合意した既存の挙動を保ち、契約による拒否と変更の検出を確認する |
| 仕様変更 | 許可する操作、必要な前提、期限、結果の意味を変える | 変更前後の要求を明示し、変更後の振る舞いを別に検証する |
| 既存不具合の修正 | 明記仕様に反する既存の挙動を直す | 仕様の根拠と変える挙動を示し、構造移行に黙って含めない |

禁止する操作を足すときは、その禁止が明記仕様なのか、今回合意する変更なのかを区別する。「DCA にするため」という理由だけで、従来許可されていた操作を禁止しない。

既存の挙動が安全か正確か分からないときは、事実と未決を残す。確認できた範囲の構造移行は進められる。未決の業務方針を既定の動作で埋めない。

## refactor の基本手順

| 段階 | 行うこと | 次へ進む条件 |
| --- | --- | --- |
| 1. 対象確認 | 対象フロー、入口、作業場所、既存の記録とソースの対応を確認する | 今回の対象と、有効な記録、要再確認の範囲が分かっている |
| 2. 現状把握 | 判断、前提、結果、次の操作、状態、外部操作、利用側、別の経路を追う | 根拠付きの現状があり、推測と未決が区別されている |
| 3. 適用範囲の決定 | 維持する挙動、適用する原則、除外する範囲、変更の単位を決める | 部分適用や適用不要を含む理由と、完了条件が決まっている |
| 4. 契約の設計 | 所有者、公開する値の意味、発行条件、利用時の確認、再判断する利用側を決める | 型で拒否する誤用と、実行時に守る条件が分かれている |
| 5. 段階的な変更 | 合意した単位で構造を変え、各段階の入口と状態の所有を明確にする | 新旧の経路の対応、保証できる範囲、残る迂回経路が分かっている |
| 6. 検証 | 既存の挙動、契約、実行時の条件、代表的な仕様変更への追従を確認する | 実際の結果、環境の制約、失敗と未検証が記録されている |
| 7. 到達点の記録 | 達成した範囲、未完了の理由、次の作業を外部記録に残す | 再開できる記録と、範囲を限った結果報告がある |

これは refactor の作業手順であり、他の Skill を順に実行する処理列ではない。既存の有効な調査や合意は再利用できる。

## 各段階で保つもの

判断と操作の所有。業務判断を Adapter、UI、組み立て処理へ移して、Core の見た目だけを整えない。Core が状態と操作の受付を所有し、必要な外部操作を Port 経由で進める構成を扱う。Core 全体の純粋関数化は必須ではない。[S01] 移行中に状態を二重に持つときは、どちらを正とし、どの操作で同期するかを決める。同じ副作用を新旧の両方から実行する経路を作らない。

契約の意味。確認済みの入力、成立の履歴、現在有効な観測、操作券を、一つの汎用 DTO にまとめない。対象や時点が違う値を、内容が同じだからという理由で流用しない。保存と復元を含むときは、履歴の復元と、現在の操作前提の再発行を分ける。[S06]

利用側への変更の伝播。仕様変更で見直す利用側が、契約の違いを受け取れるようにする。コンパイルエラーを消すためだけの else、optional な引数、互換の操作を足さない。必要な差を Boolean や null にまとめるときは、利用側の判断まで追って妥当性を確かめる。[S03]

## 新旧の併存

新旧の併存は認める。併存中は、操作と経路ごとに保証の範囲を示す。

| 状態 | 報告できること |
| --- | --- |
| 新しい経路だけを検証した | その経路について確認できた保証 |
| 別の業務操作が未移行である | 今回の範囲を完了とし、別の操作を対象外として残せる |
| 同じ操作への旧経路が契約を迂回できる | その操作全体の移行完了とは報告できない |
| 旧い入口が残るが、迂回せず同じ合意済みの前提を強制する | 入口が残ることだけで未完了とせず、主張する保証ごとに確認する |
| 実行時は拒否するが、禁止する利用コードがコンパイルできる | 実行時の拒否と型による拒否を、別々に報告する |

比較 C3 では、必須の資格証明を渡さない互換の操作を足すと、同じ利用コードがコンパイルできる。実行時の結果だけでは、型による拒否の保証を代替できない。[S04]

## 未決の事項と環境の不足

未決の事項が公開契約や許可する操作に影響するときは、選択肢と影響の範囲を示し、interview で必要な判断を確認する。独立して進められる作業まで一律に止めない。

ビルド環境や SDK が足りないときは、実施できた検証と未検証を分ける。推測で成功を補わず、必要な確認を完了条件に残す。

## 完了と部分的な到達点

対象範囲の完了は、合意した挙動と原則が反映され、必要な検証が満たされ、該当する操作の契約の迂回経路が解消された場合に限る。具体の条件は [検証](verification.md) に従う。

部分適用では、完了した範囲と未移行の範囲を示す。適用不要では、判断契約を足す必要がない理由と、調べた範囲を示す。どちらの場合も、調査、合意、進捗は対象リポジトリの外に記録する。
