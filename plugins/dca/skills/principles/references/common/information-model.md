# 情報モデル

map、scan、interview、refactor が、調査結果・仕様・判断・検証結果を同じ分類で扱うための共通資料。出典の記号（S01 など）は [同梱思想の索引](../index.md) で引く。

## 情報の分類

一つの記述に異なる種類の情報を混ぜない。記述ごとに次の分類と根拠を付ける。

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| 事実 | 対象のソース、設定、実行結果から確認したこと | 現在の実装の説明として書く。正しい業務仕様とは限らない |
| 明記仕様 | 文書または利用者との合意で明示された要求 | 適用範囲と根拠を残し、実装との一致を確認する |
| 推測 | 命名、構造、既存の挙動から考えられる意図 | 推測と分かる形で書く。修正の必須条件に昇格させない |
| 未決 | 複数の解釈があり、必要な判断が定まっていないこと | 判断が必要な範囲を特定し、interview へ渡す候補にする |

ソースを読んで分かった事実と、動作を実行して確認した事実は区別する。テストがあることだけでは、そのテストの成功も業務上の正しさも主張しない。テストを仕様の根拠にするときは、その位置付けを書く。

根拠が矛盾するときは両方を残す。優先関係が分からなければ未決にする。新しい実装を見つけたことだけで、既存の明記仕様を書き換えない。

## 調査と合意の単位

基本の単位は、対象プロジェクトの中の一つの業務フローである。そのフローの中で、操作・判断・契約・利用側を対応付ける。

| 項目 | 残す内容 |
| --- | --- |
| 対象 | リポジトリと作業場所、フロー、含める操作、除外する範囲 |
| 操作 | 入口、必要な前提、結果、結果ごとに許される次の操作 |
| 判断 | 何を決めるか、現在の所有者、合意した所有者、判断の時点 |
| 契約 | 公開する型や操作、値が表す事実、発行者、利用条件 |
| 状態 | 状態を所有する場所、遷移、同時実行や古い応答の扱い |
| 外部操作 | 発生条件、呼び出しを所有する場所、実装との接続 |
| 利用側 | 結果や前提が変わったときに再判断が必要な箇所 |
| 迂回経路 | 同じ操作に届く別の入口、旧経路、前提を省ける経路 |
| 検証 | 主張したい保証、確認方法、実施結果、未検証の事項 |

現在の構造と目標の構造は別々に持つ。名前が Core、Repository、UseCase であることだけを理由に、判断の所有者を決めない。判断の所有者、公開する値の意味、発行箇所、再判断する利用側を確かめる。[S01]

全項目を埋める必要はない。取得できていない項目は不明のまま残し、理解したことにしない。

## 根拠、合意、検証を分ける

次の三つを同じ「確認済み」にまとめない。

| 種類 | 残すもの | 変更があったとき |
| --- | --- | --- |
| 調査根拠 | ファイルや設定の位置、ソースの版、観測した内容 | 関連する箇所が変われば読み直す |
| 業務上の合意 | 合意の内容、対象範囲、理由、合意の出所 | HEAD が変わっただけでは破棄しない。仕様変更や矛盾があれば見直す |
| 検証結果 | 実行した対象、方法、期待結果、実際の結果、制約 | 対象や検証条件が変われば適用できるかを見直す |

ここでの調査根拠は、DCA の証明書や操作券のような業務上の証拠値とは別のものである。業務上の証拠値は、何を、誰について、いつ確認した値かを契約として調べる。型が同じでも、対象や時点が一致する保証は別に要る。[S06]

## 指摘の種類

| 種類 | 判定条件 | 次の行動 |
| --- | --- | --- |
| 違反 | 適用対象の原則、または合意した契約・依存の制約と、実装が一致しない | 根拠、該当箇所、影響する保証を示し、修正や検査を検討する |
| 仕様不足 | 許可する操作、判断の条件、所有者に複数の解釈が残り、意図する振る舞いを決められない | 解釈と影響を示し、人が決める判断を絞る |
| 矛盾 | コード、仕様、テスト、合意などの根拠が互いに一致しない | 食い違う根拠を並べ、優先関係と変更の意図を確認する |
| 検証不足 | 主張する保証を裏付ける検証結果がない、または現在の対象に有効か分からない | 必要な検証と再確認の条件を示す。違反とも成功とも断定しない |
| 追加調査 | ソース、仕様、環境を十分に確認できず、指摘の種類を決められない | 不足を示し、調べられる事実を確認する |
| 改善候補 | 現状は契約を満たしているが、理解や変更の追跡を改善できる | 任意の提案として示す。完了の必須条件に加えない |

推測だけを根拠に構造の違反と判定しない。たとえば来場時の資格の再確認は、基準の仕様にはなく、変更実験 I で加わる業務条件である。一般的な正しさとして導入先に当てはめない。[S05]

## 結果の形式

各 Skill は、必要な範囲で次を返す。

1. 対象フロー、操作、今回扱った範囲。
2. 事実・明記仕様・推測・未決を区別した結果と、その根拠。
3. 適用する原則と、全面適用・部分適用・適用不要の判断理由。
4. 提案、合意、実施した変更の区別。
5. 確認した保証、実際に行った検証、未検証の範囲。
6. 残る迂回経路、未決の事項、次に必要な作業。

適用不要は失敗ではない。未決や未検証が残っているのに、根拠なく適用不要と結論しない。新旧の併存中は、確認できた操作と経路に限って保証を述べる。
