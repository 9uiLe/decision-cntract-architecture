# 検証

移行で主張する保証を、既存の挙動、型、Lint、実行時の条件、仕様変更への追従に分けて検証するための共通資料。refactor と lint が主に使い、scan は検証不足を判定するときに読む。

コンパイルが通ったことだけを、移行完了の根拠にしない。[S02]

## 保証に対応する検証

| 確認したいこと | 主な方法 | 判定で確認するもの |
| --- | --- | --- |
| 合意した既存の挙動が維持される | 既存のテストと、必要なフローの確認 | 正常系に加えて、失敗・不明・復旧の遷移、外部操作、表示への受け渡し |
| 未確認の入力や別種の操作券を渡せない | 型と公開シグネチャ、負例のコンパイル | 期待した箇所と理由で拒否されること |
| 正規の利用側が使える | 正例のコンパイル | 通常の利用側と同じ境界と依存で成功すること |
| 証拠値を発行元の外で作れない | 可視性、宣言の検査、負例のコンパイル | 公開コンストラクタ、複製、継承で発行条件を迂回できないこと |
| 結果が増えたときに、利用側の対応漏れが分かる | 網羅的な分岐と、代表的な変更実験 | 再判断すべき箇所に期待した診断が出ること |
| 禁止する依存や呼び出しを防ぐ | モジュール、import、型解決付きの Lint | 合意した所有者と接続の制約に一致すること |
| 同じ型の別対象、古い値、時刻の境界を拒否する | 時刻や応答を制御した実行テスト | 対象、鮮度、状態、境界値が合意した条件を満たすこと |
| 重複した操作や古い応答で状態が壊れない | 並行、再操作、応答順のテスト | 外部要求の数、要求 ID、状態の所有、応答を反映する条件 |
| 同じ操作への別経路が契約を迂回しない | 入口の追跡と、経路に応じた検証 | 新旧の経路を含め、主張する操作に届く条件 |
| 表示が同じ操作の更新が画面に届く | 画面をホストし、券だけと実行先だけの更新後にそれぞれボタンを押す | 実際に届いた券の同一性、実行先、操作、引数と、維持した画面状態 |

表のすべてを毎回足さない。対象の保証に必要な検証を選ぶ。既存の有効なテストを使い、実装をなぞるだけのテストを増やさない。

## 既存の挙動の維持

維持する挙動は、明記仕様と合意に基づく。既存の実装から観測した動作も記録する。不具合と分かった挙動は、無条件に正解として固定しない。

移行に伴って挙動を変えるときは、仕様変更か不具合修正として切り分ける。変更前後の差と、変更後に期待する振る舞いを示す。

外部操作は、戻り値に加えて、必要に応じて要求の有無、回数、ID、順序を確かめる。「拒否した」という表示だけで、禁止した外部要求が出ていないと判断しない。

## 型と Lint の確認

型による保証は、通常の利用側と同じコンパイル境界で確認する。Core と同じモジュールや特別な可視性を持つテストだけで、外部の利用側から作れないと結論しない。[S01]

負例は、一つの誤用を理由に失敗したと判断できる形にする。期待するファイル、位置、診断を照合し、依存の不足や別の構文エラーによる失敗を成功扱いしない。[S02]

Lint を導入するときは、対象の設定と検出力の範囲を確認する。

- 合意した違反を検出する負例と、許可するコードを拒否しない正例を持つ。
- 型解決が要る規則では、対象の source set と classpath が設定されていることを確認する。
- サンプル固有の package、Port、依存の向きを、そのまま導入先の普遍的な規則にしない。
- ルールが検出しない迂回は、別の検証かレビューに残す。

たとえば既存の RequiredEvidenceParameter は、存在する証拠引数が省略可能でないかを検査する。証拠引数を持たない別の操作が足されることまでは保証しない。比較 C3 のような利用側の負例が、別に要る。[S03][S04]

## 実行時の条件の確認

型が一致していても、対象、現在の状態、時刻、操作の回数が正しいとは限らない。[S06]

対象に必要な条件を選び、次のような境界を確認する。

- 同じ型だが、別の人、別の資格、別の予約に対する値。
- 確認し直した後の古い値、処理中の重複した操作、古い応答。
- 期限の直前、ちょうど、直後。
- 外部操作が成立した可能性を残したままの応答の欠落、照会の失敗、未発見。
- 画面の再生成や再購読が、新規要求の再送を起こさないこと。
- 非同期の再確認の最中に、期限や他の状態が変わる場合。

これらは検証の観点であり、具体的な許可条件は導入先の仕様から決める。DCA サンプルの予約期限や資格条件を、別の業務に自動で当てはめない。

操作を持つ画面では、古いイベントが元の券のまま Core に届くかも確かめる。上流の等価比較で新しい券が失われる問題は、古い券を Core が実行時に拒否することと分けて記録する。画面を操作できない場合は、値の比較やハンドラーの直接実行で観測した範囲を示し、画面の検証は未実施として記録する。[S01][S02]

## 代表的な仕様変更による確認

対象の設計目的に合う代表的な変更を選び、見直しが必要な箇所に診断やテストの失敗が届くかを確認する。サンプルの課題をすべて再現する必要はない。

| 変更の種類 | 確認すること |
| --- | --- |
| 結果のケースの追加 | 未対応の判断や画面の変換を検出できるか |
| 操作の前提の追加、操作の削除 | 旧い利用コードが期待した理由で拒否されるか |
| 外部の形式だけの変更 | Adapter の解釈とテストで確認し、意味が変わらない業務契約に不要な変更が広がらないか |
| 同じ型の条件式を誤る変更 | コンパイルでは検出できない境界値の誤りを、実行テストが検出するか |

変更実験は一時コピーなどで隔離し、実験用の仕様変更を実際の移行成果物に残さない。変更の前に、何が失敗するべきかを明示する。予想外の失敗で実験が止まっただけの状態を、検出の成功にしない。

対応後まで確認するときは、新しい仕様を満たすことと、影響しない範囲が維持されることを確かめる。[S02]

## 検証結果の記録

結果は保証と対象のソースに結び付け、次を残す。

- 検証した対象のフロー、操作、経路、source set などの範囲。
- 実行した対象のソース識別情報と、関連する設定。識別の方法は [外部記録](record-storage.md) に従う。
- 方法またはコマンド、期待結果、実際の結果。
- 判断に必要な診断やログの参照。
- 環境の制約、未検証の対象、再確認が必要な条件。

| 表示 | 意味 |
| --- | --- |
| 確認済み | 示した対象と条件で実施し、期待結果を確認した |
| 失敗 | 実施した結果、期待した保証を満たさなかった |
| 未実施 | まだ実行していない |
| 環境不足で未検証 | SDK、実行環境、依存の不足により確認できない |
| 要再確認 | 関連するソースや条件が変わり、以前の結果をそのまま適用できない |

前回の結果を参照するときは、その事実と、今回の対象に適用できることを書く。今回の再実行とは書かない。

KMP では、JVM、共通コード、Android、iOS 固有コードなどの検証範囲を示す。JVM で通ったことから、実行していないプラットフォームや UI 操作の成功を推定しない。

## 対象範囲の完了条件

次の条件を満たした範囲だけを、完了と報告する。

1. 維持する挙動と、別に合意した挙動の変更が区別されている。
2. 適用する判断契約、所有者、発行条件、利用側が実装に対応している。
3. 合意した型、Lint、実行時の条件の検証を満たしている。
4. 代表的な仕様変更で、期待する判断箇所の追跡と対応漏れの検出を確認している。
5. 該当する操作の保証を迂回する経路が解消されている。
6. 最終のソースに対する結果と、残る対象外と未検証の事項が記録されている。

適用しない検証には理由を残す。環境不足や未実施を成功と読み替えない。新しい経路だけが条件を満たすときは、その範囲の到達点として報告できる。同じ操作全体の完了には広げない。
