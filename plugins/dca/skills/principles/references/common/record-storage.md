# 外部記録

調査、合意、移行の進捗、検証結果を、対象リポジトリに書き込まずに保存し、別の会話から再開するための共通資料。map、scan、interview、refactor が記録を読み書きするときに、この資料を直接読む。

## 保存と識別の道具

記録の読み書きは、この Plugin の `scripts/dca_state.py` で行う。この資料から見て `../../../../scripts/dca_state.py` にある。ソースの識別と比較は `scripts/dca_source.py` で行う。どちらも `python3` で実行し、出力は JSON である。

実行できないとき、または結果が `not_saved`、`refused`、`conflict` のときは、保存済みと報告しない。対象リポジトリを代わりの保存先にしない。結果の `reason` と、書込先、選択元（`location`）を利用者に伝える。

| コマンド | 内容 |
| --- | --- |
| `dca_state.py where` | 保存先と選択元、プロジェクトの鍵、現在の変更対象、既存のフローを調べる。何も書かない |
| `dca_state.py list` | このプロジェクトの記録済みフローを、鍵、ラベル、token とともに一覧する |
| `dca_state.py read --flow KEY` | 記録を読む。更新に使う token を返す |
| `dca_state.py create --flow KEY --label LABEL` | 新しい記録を作る |
| `dca_state.py observe`、`progress`、`verify`、`agree` | `--flow KEY --expected-token TOKEN` を付け、標準入力の JSON を一つの層に反映する |
| `dca_source.py identify --path P ...` | relevant なパスの識別情報を JSON で作る |
| `dca_source.py compare --before A --after B` | 二つの識別情報を比べる |

## 保存先

保存先は、`DCA_STATE_DIR`、`XDG_STATE_HOME` の下の `dca`、`~/.local/state/dca` の順で選ばれる。明示した値は絶対パスにする。結果の `location.selected_by` に選択元が出る。

次の場所は保存先にできず、`refused` になる。

- 対象のリポジトリ、その Git 管理ディレクトリ、同じプロジェクトの他の worktree。
- この Plugin を管理するリポジトリと、Plugin のインストール先。
- 管理するディレクトリ、`record.json`、ロックのファイルが symlink や通常ファイル以外になっている場所。

記録のためだけに、導入先の CLAUDE.md、AGENTS.md、docs、設定ファイルを作らず、変更しない。許可された refactor の成果物である実装コードや契約を検査するテストは、対象リポジトリに置ける。作業の記録とは区別する。

## プロジェクト、フロー、変更対象

- プロジェクトは、Git の common-dir から決まる。別の clone は別のプロジェクトである。同じパスに別のリポジトリが置かれたときは、履歴の識別が一致せず拒否される。
- 記録は、一つのプロジェクトの一つのフローに一つだけある。
- フローの鍵とラベルは、利用者と合意して一度だけ決める。以後は変えない。
- 合意はフロー全体の層に保存する。観測、検証、進捗は、変更対象の worktree と Git ディレクトリごとの層に保存する。別の worktree の観測と検証を、現在の対象に流用しない。

## 作業の始め方

1. `where` で、保存先、選択元、プロジェクトの記録の有無、現在の変更対象を確認する。
2. `list` で、既存のフローを探す。対象のフローがあれば、利用者にそのフローで合意していることを確認してから `read` で読む。
3. 対象のフローがなければ、鍵（小文字の英数字とハイフン）とラベルを利用者に提案し、合意を得てから `create` を一度だけ実行する。
4. 利用者に、新しい記録を作ったのか既存の記録を使ったのかと、現在の変更対象（worktree、HEAD）を伝える。

別の worktree や別の clone の記録を再利用するときは、今回の対象と対応することを確認する。

## 更新の規則

- 更新は、`read` で得た token を `--expected-token` に渡して行う。`conflict` のときは、読み直して差分を確認し、黙って上書きしない。
- 記録全体を書き換える方法はない。更新は、観測の追加（`observe`）、進捗の置き換え（`progress`）、検証の追加（`verify`）、合意の置き換え（`agree`）に限る。
- 合意の更新（`agree --confirmed`）は、利用者に内容を示して最終確認を得た後だけ行う。合意を更新しても、過去の検証の対象と結果は残る。
- 検証は追記だけである。古い結果を新しい成功に上書きしない。前回の結果が使えなくなったときは、`要再確認` の検証を追加する。
- 認証情報や、無関係な個人情報を記録しない。履歴の全文や全コマンドの保存は求めない。

## ソースの識別

HEAD だけでは、調べたソースを識別できない。対象の選択と、調査や検証が依存するパス（relevant なパス）を決め、`dca_source.py identify` で識別情報を作る。識別情報は、HEAD、index、作業ツリー、無視されていない untracked のファイルの内容を、パスごとの hash で表す。内容そのものと、機微な名前のファイルの hash は記録しない。

識別が扱わない範囲は、識別情報の `coverage.notes` にある。リネームの検出、UTF-8 でない名前、symlink の先、サブモジュールの内部、無視されたファイル、環境条件は、確認済みとして扱わない。`compare` の `unconfirmed` に出た項目は、確認できていない範囲として報告に書く。

検証の前後に識別情報を作り、`verify` に `identity_before` と `identity_after` を渡す。確認済みにできるのは、前後で relevant なパスと、それ以外の変更が検出されなかった場合だけである。範囲に限界があるときは、その限界が記録に残る。dirty な一覧が上限で切れたときは、確認済みにできない。

## 再開

再開するときは、記録を読み、現在の対象と照合してから次の作業を選ぶ。`compare` で、記録した識別情報と現在の識別情報を比べる。

| 変化 | 合意の扱い | 根拠と検証結果の扱い |
| --- | --- | --- |
| HEAD が変わったが、関連するソースと構成に変化がないと確認できた | 維持する | 前回結果が使えることを記録する。今回再実行したとは書かない |
| 同じ HEAD で、関連する未コミットの変更がある | 自動では破棄しない | 変更箇所に依存する調査と検証を見直す |
| 対象の操作、利用側、迂回経路、関連する設定が変わった | 対応する合意との矛盾を確認する | 影響する保証を要再確認にする |
| worktree や対象フローが違う | 再利用できる内容を確認する | 別の対象の結果をそのまま適用しない |
| Plugin の原則や検査の解釈が変わった | 関連する合意だけを見直す | 影響する評価と検証を見直す |
| 変更の影響を判断できない | 未決のまま残す | 適用できると断定せず、必要な調査をする |

`compare` の `outside_changes` は、relevant なパスの外で変わったファイルである。新しい入口や、同じ操作に届く別の経路が加わっていないかを、このファイル名と構成の差分から Skill が調べる。過去に列挙したファイルだけを見て、安全と結論しない。

HEAD が変わったことだけを理由に、利用者との仕様の合意をすべて消さない。プロジェクト名が同じことを理由に、前回の検証の成功を引き継がない。ソースを変えた後は、変更後の識別情報と検証結果を対応付ける。途中の版に対する成功を、最終状態の成功として報告しない。

## Plugin 自体の保守成果物との区別

この資料が扱うのは、導入先のプロジェクトに対する作業の記録である。dca 自体の思想、Skill の定義、構成図の SVG は Plugin の保守成果物であり、Plugin を管理するリポジトリに置く。導入先の調査内容やプロジェクト名を、同梱思想や構成図に混ぜない。
