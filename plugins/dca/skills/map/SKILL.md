# map

対象フローの判断と保証の所在を、根拠付きで対応付ける。

## 使う場面

- 既存フローで、判断がどこに置かれているかを知りたい。
- Kotlin/JVM と KMP のコードを、呼び出し側が期待する振る舞いと対応付けたい。
- 移行の前後で、判断の所有者や保証がどう変わるかを比べたい。

## 読む資料

- [情報モデル](../principles/references/common/information-model.md)
- [外部記録](../principles/references/common/record-storage.md)
- [同梱思想の索引](../principles/references/index.md)

判断契約の用語を使うときは、索引が指す S01 を読む。

## 手順

1. 対象のプロジェクトとフローを確認する。外部記録の資料の「作業の始め方」に従い、保存先、既存のフロー、現在の変更対象を確かめる。記録があるときは、現在のソースとの対応を照合してから使う。
2. フローの入口、終了点、利用側を特定する。対象外との境界を明示する。
3. 次の六つを、コード、テスト、仕様の根拠に結び付ける。

| 対象 | 明らかにすること |
| --- | --- |
| 判断 | 何を判断し、その判断を誰が所有するか |
| 契約 | 前提、結果、許可される操作は何か |
| 状態 | 何を保持し、どこで遷移するか |
| 副作用 | 何を実行し、誰が実行を決めるか |
| 利用側 | どの結果や契約に依存しているか |
| 保証 | 利用側に何を保証し、何が未確認か |

4. 操作を持つ画面が対象なら、発行元から投影、通知、等価比較やキャッシュ、イベントが保持する値、実行先と受理判定までを対応付ける。現在の実装、文書上の仕様、利用者との合意を区別する。食い違いは図を整えるために解消したことにしない。
5. 根拠がない関係や、追跡できない分岐は、未確認として残す。必要に応じて、`scan` で調べる対象と、`interview` で決める論点を示す。
6. 調べたパスの識別情報を作り、判断と保証の対応表、根拠の一覧、未確認の事項を外部記録に保存する。関係を図で示すと理解しやすいときは SVG を添える。図には根拠のある関係だけを描く。

## 出力

- 対象フローの、判断と保証の対応表。
- 各要素の根拠の一覧。
- 未確認の事項。
- 移行の前後を比べるときは、現状と合意した変更案を区別した比較。
- 保存先、選択元、新しい記録かどうか、現在の変更対象。

## 完了条件

対象範囲の判断の所有者、契約、状態、副作用、利用側、保証を追跡できる。追跡できなかった部分も特定されている。図があることは、仕様の正しさや検証の完了を意味しない。

## 境界

- 構造の把握と可視化だけを行う。違反の確定、仕様の決定、コードの変更はしない。
- DCA に適した形を、現状として描かない。部分適用や適用不要の判断に使える現状を示す。
- dca 自体の構成図は `overview` が扱う。
- 他の Skill の事前の実行を、開始の条件にしない。`scan` や `interview` の結果があれば、現在の対象と一致するかを確かめて使う。

## 他の Skill との関係

- 引き継ぎ skill:scan: 追跡できない関係を、調べる対象として渡す
- 引き継ぎ skill:interview: 食い違いや未確認から、決める論点を渡す
- 生成 artifact:external-record: 判断と保証の対応表、根拠の一覧、未確認の事項
